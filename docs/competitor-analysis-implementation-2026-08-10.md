# تطبيق تحليل المنافسين على ابتكار تك

**التاريخ:** 10 أغسطس 2026  
**الفرع:** `feature/competitor-analysis-2026-08-10`

## الحكم التنفيذي المطبق

ابتكار تك تُبنى كمنصة أم للحلول والخدمات الرقمية، وليست متجر خدمات سلة فقط ولا موقع ثيم واحد. التنفيذ الحالي يفصل بوضوح بين:

1. **الحلول والخدمات** — يبدأ العميل من الهدف أو نوع التنفيذ.
2. **المنصات** — صفحات تخصصية مثل سلة وزد وShopify وWooCommerce وWordPress.
3. **المنتجات الأصلية** — مثل ثيم ثراء، بصفحة قرار شراء مستقلة.
4. **الأعمال** — دليل اجتماعي وحالات تُنشر فقط عند توفر دليل وإذن.
5. **المعرفة** — مقالات وأدلة وحالات وFAQ وموارد مرتبطة بقرار العميل.

---

## ما تم تطبيقه

### 1) Information Architecture والهيدر

تم اعتماد:

- الرئيسية
- الحلول والخدمات
- المنصات
- منتجاتنا
- أعمالنا
- المعرفة
- عن ابتكار
- CTA: اطلب عرض سعر

`الحلول والخدمات` تجمع مسارين داخل Mega Menu: البدء من الهدف أو اختيار نوع التنفيذ.

`المعرفة` أصبحت Mega Menu مستقلة تحتوي مقالات، أدلة، دراسات حالة، FAQ وموارد.

تم تحديث Desktop / Mobile / Footer داخل:

`assets/js/page-shell.js`

كما أزيل البريد غير الموثق من الفوتر حتى لا تُنشر بيانات اتصال غير معتمدة.

### 2) الصفحة الرئيسية

تم إعادة بناء `index.html` كـ Goal-led Router بدل صفحة عرض بصري فقط.

التسلسل:

1. Hero يعرّف ابتكار تك كمنصة أم.
2. Build / Brand / Connect / Grow.
3. ابدأ من هدفك: أطلق / حسّن / اربط / نمِّ.
4. مرحلة المشروع: جديد / قائم / مشكلة / توسع.
5. ست عائلات حلول وخدمات فقط.
6. تخصص التجارة الإلكترونية.
7. مسار متخصص لسلة.
8. منتجات ابتكار تك مع Spotlight لثراء.
9. الأعمال والحالات دون Claims غير موثقة.
10. منهجية التنفيذ.
11. المعرفة.
12. CTA لطلب عرض سعر.

### 3) صفحة جميع الحلول والخدمات

تم إعادة بناء `services.html` كنظام تجاري قابل للاكتشاف:

- البداية من الهدف.
- مرحلة المشروع.
- بحث داخل الخدمات.
- فلاتر حسب العائلة والمنصة.
- ثماني خدمات رئيسية بدل عشرات المهام الصغيرة.
- كل بطاقة توضح: النتيجة، لمن تناسب، صيغة التسعير والمدة.
- لا أرقام سعر أو مدة غير معتمدة.
- شرح لماذا يثبت النطاق قبل التنفيذ.
- ربط بالخدمات والمنصات المناسبة.

المنطق التفاعلي موجود في:

`assets/js/service-catalog.js`

والنظام البصري المشترك موجود في:

`assets/css/pages/commercial-system.css`

### 4) صفحة خدمات سلة

تم إعادة بناء `salla.html` حول رحلة التاجر:

1. Hero متخصص.
2. حالة المتجر: جديد / قائم / مشكلة / جاهز للنمو.
3. ست خدمات أساسية قابلة للمقارنة.
4. السعر والمدة بصيغة شفافة حتى اعتماد الأرقام.
5. فحص حدود المنصة والثيم والتطبيقات.
6. رحلة تنفيذ.
7. FAQ.
8. CTA منظم.

CSS الخاص بها:

`assets/css/pages/salla.css`

### 5) قالب الخدمة المفردة

تم تحويل `product-page-optimization.html` إلى المرجع القياسي لـ Productized Service Page.

القالب الحالي يحتوي:

- Breadcrumb.
- النتيجة الرئيسية.
- Decision Card.
- لمن تناسب / لا تناسب.
- المتطلبات قبل البدء.
- نطاق الخدمة.
- المخرجات.
- ما لا يدخل تلقائيًا.
- خطوات التنفيذ.
- طريقة القياس بدون وعد مبيعات.
- خدمات مرتبطة.
- FAQ.
- CTA منظم.

هذا القالب هو المرجع الذي يجب نسخه عند بناء خدمات مفردة جديدة.

### 6) ثيم ثراء كمنتج مستقل

تم إعادة بناء `tharaa.html` كـ Product Decision Page بدل بطاقة خدمة.

تتضمن:

- وعد المنتج.
- القطاعات المناسبة.
- بيانات قرار الشراء.
- أهم 8 مزايا فقط.
- تجربة الصفحة الرئيسية.
- صفحة المنتج.
- الجوال.
- فصل الترخيص عن خدمة التركيب والتخصيص.
- الإصدار وآخر تحديث وChangelog.
- الدعم والتوثيق.
- CTA للديمو والشراء الرسمي.

القيم غير الموثقة لا يتم اختلاقها. روابط الديمو والشراء والسعر والإصدار وآخر تحديث مرتبطة مركزيًا بـ:

`assets/js/site-config.js`

وعند بقاء القيمة بصيغة `[TODO: ...]`، يقوم `service-catalog.js` بتعطيل CTA وعرض حالة انتظار بدل رابط مكسور أو معلومة وهمية.

### 7) مركز المعرفة

تم بناء `knowledge.html` بخمسة مسارات واضحة:

- `#articles` المقالات.
- `#guides` الأدلة.
- `#cases` دراسات الحالة.
- `#faq` الأسئلة الشائعة.
- `#resources` الموارد.

لا توجد حالات نجاح أو أرقام مختلقة؛ بنية النشر جاهزة لإضافة المحتوى الحقيقي تدريجيًا.

### 8) الطلب المنظم

تم تحديث `contact.html` ليتوافق مع تصنيف المنصة الجديد:

- الهدف.
- المرحلة.
- المنصة.
- التوقيت.
- تفاصيل الحالة والرابط.

واتساب ليس نظام الطلب الأساسي. كما لا يتم عرض بريد أو رقم غير معتمد.

النموذج الحالي Front-End فقط ويحفظ الطلب محليًا للمعاينة؛ لا يدعي إرسال الطلب قبل ربط Backend/CRM.

## قواعد غير قابلة للكسر

- لا نختلق سعرًا أو مدة أو نسبة نمو.
- لا نعرض شعار عميل أو نتيجة دون إذن ودليل مناسب.
- ثراء منتج مستقل؛ التركيب والتخصيص خدمة منفصلة.
- واتساب قناة مساندة وليس نظام الطلب الوحيد.
- كل خدمة توضح الملاءمة والنطاق والاستثناءات والمراجعات والتسعير والمدة قبل التنفيذ.
- كل منتج يملك ديمو وشراء رسمي ودعمًا وتوثيقًا وإصدارًا وسجل تحديث عند توفر البيانات الحقيقية.
- الجوال وRTL أساسيان في المراجعة.
- لا يُكتب محتوى SEO شكلي فقط لزيادة عدد الصفحات.
- لا يوضع نص مهم داخل صورة.

## البيانات الرسمية المطلوبة قبل النشر النهائي

هذه البيانات ما زالت غير متوفرة بشكل موثوق داخل المشروع، ولذلك بقيت محمية كـ TODO أو حالة انتظار:

### ثراء

- رابط الديمو الرسمي.
- رابط الشراء الرسمي في متجر سلة.
- السعر الرسمي.
- الإصدار الحالي.
- تاريخ آخر تحديث.
- سجل التغييرات العام إذا كان سيظهر للعملاء.

### ابتكار تك

- الدومين الرسمي النهائي.
- البريد الرسمي.
- رقم الهاتف وواتساب الرسميان.
- العنوان إن كان سيُنشر.
- روابط الشبكات الاجتماعية.
- Backend/CRM Endpoint للنماذج.
- سياسة الخصوصية النهائية المرتبطة بالإرسال.

### الخدمات

- أسعار ثابتة أو أسعار ابتدائية معتمدة للخدمات التي يمكن Productize تسعيرها.
- مدد تنفيذ معتمدة.
- عدد المراجعات لكل خدمة.
- 3–5 حالات عمل حقيقية مسموح بعرضها مع دليل النتيجة.

## ما لم يُعتبر مكتملًا بعد

### اختبار المتصفح الفعلي

لا يتم اعتبار التنفيذ جاهزًا للدمج قبل اختبار فعلي على:

- 360px.
- 390/430px.
- 768px.
- 1024px.
- Desktop.

مع التحقق من:

- Mega Menus.
- Mobile Menu.
- RTL.
- Keyboard / Escape / Focus.
- عدم وجود Horizontal Overflow.
- Search & Filters في الخدمات.
- FAQ.
- تعطيل روابط ثراء غير المعتمدة.
- نموذج طلب السعر متعدد الخطوات.

### الأداء

بعد الاختبار البصري:

- Lighthouse.
- مراجعة تحميل الخطوط.
- الصور والأبعاد وLazy Loading.
- تقليل CSS/JS غير المستخدم في الصفحات القديمة.

## نتيجة Compare الحالية

الفرع مبني فوق `main` دون Behind عند آخر مراجعة، والتغييرات محصورة في طبقة الموقع التسويقية المطلوبة. قبل الدمج يجب إعادة `compare` ومراجعة الملفات المتغيرة مرة أخيرة.

## معيار الدمج

لا يُدمج الفرع إلى `main` إلا بعد:

1. إدخال البيانات الرسمية المطلوبة أو قبول حالات الانتظار بوضوح.
2. اختبار المتصفح والجوال وRTL.
3. مراجعة جميع الروابط الداخلية.
4. اختبار البحث والفلاتر والنماذج وFAQ.
5. فحص الأداء والإتاحة الأساسي.
6. مراجعة Compare/Diff النهائي.
